# Database

Schema reference and maintenance procedures for the Backlog Registration Portal. Setup, deployment
and environment variables are in the [README](../README.md); working knowledge is in
[MAINTAINER_NOTES.md](MAINTAINER_NOTES.md).

> Some details here may be outdated. The migrations in
> `backend/backlog/src/main/resources/db/migration/` are the source of truth — check them, or the
> live schema (`\d+ <table>` in `psql`), before relying on a detail.

## Schema

Flyway owns the schema (`ddl-auto=validate`): Hibernate only checks that entities match.
Migrations `V1`–`V9` are applied in production and are **frozen** — Flyway checksums each file,
comments included. Any change is a new `V<next>__description.sql`; never edit an applied one and
never hand-apply DDL. `V1__baseline.sql` is a snapshot of the original database.

The tables below are the state after `V9`. All `varchar` columns are `varchar(255)` unless a length
is given; all timestamps are `timestamptz` (stored as instants, printed in Asia/Kolkata). Every
`id bigint` primary key is `GENERATED BY DEFAULT AS IDENTITY`. Nullable unless marked NOT NULL.

## Maintenance

`psql` and `pg_dump` need the **libpq** connection string
(`postgresql://<user>:<password>@<host>/<db>?sslmode=require`), not the JDBC `DB_URL` the app uses.

### Backups

Neon's free tier keeps very little restore history, so take your own backups once real data is in
the database — at least before every release and before any migration:

```bash
pg_dump "postgresql://<user>:<password>@<host>/<db>?sslmode=require" \
  --no-owner --no-privileges -f "dump-$(date +%F).sql"
```

Restore into an empty database with:

```bash
psql "postgresql://<user>:<password>@<host>/<db>?sslmode=require" < dump-YYYY-MM-DD.sql
```

`--no-owner --no-privileges` lets the dump restore under a different database role. Never commit a
dump — it contains student data. `.gitignore` already ignores `dump*.sql` at the repo root.

### Schema drift check before a release

Migrations are the intended source of truth, but a production database can still drift from them
(a column added by hand, a past emergency fix). Before a release, compare the two:

1. `pg_dump --schema-only` the production database.
2. Build a scratch database from the migrations (start the app or run the tests against an empty
   Postgres) and `pg_dump --schema-only` it.
3. Strip `--` comments, `SET` lines, `\restrict` lines and blank lines from both, then `diff` them.

Any difference means production has something the migrations would not create (or the reverse) —
fix it with a new migration. This is manual on purpose: CI cannot reach the production database
and should not hold its credentials. It has caught real drift on this project more than once.
